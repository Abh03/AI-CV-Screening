# Stage 3 evidence selection protocol

Prompt v14 uses `CompactSentenceSelectionOutput` for configured real providers. The provider supplies scores, suitability rationales, selected sentence handles, flags, summary, and the exact `evidence_scope`. It cannot supply factual claims or quotes. Python resolves selections into the original stable evidence IDs and constructs each factual claim/quote verbatim from a complete source sentence.

Provider handles (`S1`, `E1`, `P1`, `D1`, etc.) are short request-local transport names. S/E/P/D select SKILLS/EXPERIENCE/PROJECTS/EDUCATION. The request-local schema enumerates supplied handles for each assessment, and enumerates exactly one valid evidence_scope. The resolver checks scope independently; it binds candidate ownership, the full supplied registry and the handle-to-stable-ID mapping. A changed candidate, registry or mapping cannot reuse an old selection. Stable IDs, not transport ordinals, are stored in verified claims. Old positional tags such as SKILLS:1 are not valid provider handles.

Each `evidence/p/e` row contains an unchanged complete sentence and its allowed category handles. Its parent `p.c` retains source category. A physical sentence is sent once across categories. Full CV passages are kept in original source order to preserve role/date/responsibility context. Retrieval copies are suppressed only when their text, after whitespace/header normalization, occurs contiguously with word boundaries in a supplied full-CV sentence of the same assessment category and source category. Separate physical CV occurrences are never merged, even if text is identical. Unmatched retrieval text remains. The immutable registry retains all original references, including deduplicated copies, for provenance/audit; only transport text and IDs are compacted.

Stable IDs bind candidate ownership, assessment category, original document/chunk identity, source category/location/text and sentence offsets. `sentence_start`/`sentence_end` are offsets in the original chunk; `source_location` retains parent provenance. PDF line wraps and decimals do not become sentence boundaries. Segmentation is lexical, not a linguistic parser. Omitted passages are never selectable and omissions still require review.

Historical v12/v13 outputs remain readable through their original compatibility schemas/resolvers. `source-excerpt-v1` rejects unsupported paraphrases, dropped recognized qualifiers/negation, fabricated quotations and unsupported numbers. Mock evaluations retain their existing synthetic development/test format. Custom legacy test providers retain their compatibility path.

Budgets include system prompt, user XML, the actual compact schema, chat framing and completion allowance. GPT-OSS uses the pinned official tokenizer when available; schema/chat rendering retains a 128-token estimate margin. A conservative byte estimate is the fallback for other models or absent local assets. Docker provisions only tokenizer.json, never GPT-OSS generation weights, at build time. Local development uses models/gpt-oss/tokenizer.json or GROQ_TOKENIZER_PATH. A configured/mismatched tokenizer fails validation rather than silently using untrusted counts.

Groq input admission is checked separately from the model's total context limit (input plus maximum completion allowance). Recent observed full-context calls demonstrate that completion allowance is not a prepaid hard input-admission deduction. The shared minute limiter conservatively reserves the whole configured minute bucket for large requests; it still spaces calls and protects account throughput. Actual provider accounting may differ from local estimates, so pilot preflight and response metrics remain required.

Compaction does not prove arbitrary rationale/summary prose or suitability judgments. Candidate/category ownership, exact claims, numeric/negation checks, injection checks, omission warnings and material-flag review requirements are unchanged.
